# 插件更新设计与执行基线

本文记录“管理插件”和插件包更新能力的产品与实现边界。当前实现状态以代码为准；未完成能力不得在界面或交付说明中宣称可用。

## 目标

- 在“管理插件”中显式检查指定实例 Profile 的直接依赖，并更新可验证来源。
- 检查与写入始终绑定 `instance_id`；写入前阻止同 Home 实例运行。
- 保留插件启停状态，展示真实版本结果和完整安装日志。
- 插件包复用逐插件检查结果；新增或移出清单的条目不自动安装或卸载。

## 来源策略

| 来源 | 检查与更新策略 |
|---|---|
| npm semver 范围 | 查询 registry，在原范围内选择最高匹配版本；安装明确版本并核验 |
| npm dist-tag | 跟随原 tag，不自动切换通道 |
| npm 精确版本 | 标记固定，不默认更新 |
| GitHub/Git | 必须能证明已安装提交与远端 ref 后才开放；固定提交不追踪 HEAD |
| HTTP(S) 压缩包 | 标记固定；只有可信目录提供可关联的新规格时才可更新 |
| 本地及未知协议 | 显示无法自动判断，不猜测命令 |

`repository` 元数据只用于展示，不能替代 Profile 中的依赖来源。网络失败、缺少基线和解析失败都属于“无法判断”，不能显示“已是最新”。

## 操作契约

检查是只读网络操作。应用更新时，后端根据 Profile 当前依赖重新计算目标，并比较预览中的当前版本、来源规格和目标版本；任一变化都以冲突中止。

更新前保存 `package.json`、`pnpm-lock.yaml` 和 `pnpm-workspace.yaml` 的原始内容。安装继续走当前选中 DSH 运行时的 `dsh plugin --profile ... add ...`，复用 pnpm 选择、完整性修复、`allowBuilds`、日志和取消机制。完成时核对直接依赖、实际版本及启停状态。失败时恢复原文件、通过原生 CLI 重建旧依赖并再次核验；恢复失败必须明确报告。

## 插件包语义

插件包是分发清单，不是 Profile 内的独立安装实体。“检查包内更新”只检查其中已安装的插件。新增条目只提示，移出条目继续保留，版本倒退不默认执行，来源冲突要求单独处理。

## 分阶段状态

- [x] npm 范围和 dist-tag 的检查、单项更新、并发变化检查、启停状态保留、失败恢复尝试与结果核验。
- [x] 管理页和插件包详情页的检查入口、版本提示、单项更新入口。
- [ ] 更新预览对话框、勾选批量更新和持久化后台 operation id。
- [ ] Git 分支/标签/提交的 lockfile 基线解析、远端检查与可验证恢复。
- [ ] 压缩包通过当前目录重新解析新规格，并展示插件包清单新增/移出/冲突状态。
- [ ] 启动器异常退出后的未完成事务恢复入口。

## 验收要求

至少覆盖 npm 范围内更新、dist-tag、精确版本、停用插件更新、预览后依赖变化、共享 Home 运行、断网、更新后仍是旧版本、安装失败、恢复失败、实例切换、取消、插件包新增/移出，以及中英文和窄窗口显示。涉及 Rust 后端时重新编译并重启 `pnpm tauri dev` 后做一次性 Home 真机验收。
